Memory Intel (npm: `memoryintel`) is a persistent, cross-session project-memory tool for AI coding agents (Claude Code, Cursor, Codex, Gemini CLI). A person sets it up once per project by asking an agent to (set up persistent memory here - the memoryintel skill runs `memoryintel init`); after that, agents load `.memoryintel/` context automatically at session start and update it on their own judgment when something meaningful changes.

The repo itself was rebuilt from scratch this cycle: a commit had gone out from the user's company network and gotten flagged on the company's side, so the whole GitHub repo was deleted and recreated with fresh git history (single root commit, no trace of the old one), renamed memory-intel -> memoryintel throughout (plugin id, marketplace id, skill directory, all repo URLs) to match the npm package name, which was already memoryintel. The old npm package had also been fully unpublished in the process. Since npm permanently blocks reusing any version number a package name has ever published-then-unpublished, 0.1.0/0.1.1/0.1.2 are all dead forever on this name - republished fresh as 1.0.0 (the user's explicit choice, to mark this as a real clean start rather than leaving a silent 0.1.x gap), now live on the registry with npm Trusted Publishing (OIDC, no token secret) wired to release-please.yml for future releases.

The CLI core (init/scan/import/load/update/status/check-stop/dashboard) is fully built and tested (238 tests passing, all green on the 3-OS CI matrix). Two new brownfield-onboarding commands this cycle, in order of when an agent should reach for them: `memoryintel import` pulls memory-bank/ (Cline/Roo/Kilo-Code convention), ARCHITECTURE.md, and README.md's lede verbatim into mapped .memoryintel/ sections, reusing the existing runUpdate pipeline wholesale - deliberately mechanical, tagged as raw/unfiled, never summarized. `memoryintel scan`, added right after, covers the actual more-common case per the user's own correction: a project with neither memory-bank/ nor ARCHITECTURE.md, just code - someone who already has memory-bank/ organized wouldn't need memoryintel as much in the first place. scan never writes anything; it prints a read-only digest (detected stack, git-churn ranking, a JS/TS/Python local import-graph ranked by in-degree as a cheap proxy for "architecturally central", and other docs found in the tree) for the agent to read and use its own judgment on. Two real bugs were found and fixed by dogfooding scan on this repo before shipping: the import-graph resolver initially missed TypeScript's own NodeNext/ESM convention of a .js specifier pointing at a real .ts file (would have found zero hits on this project's own code), and .memoryintel/ itself was leaking into the doc-discovery and churn output as if it were source material.

Also this cycle: deleted the dead .memoryintel/intelligence/{entities,metadata,relationships}.json scaffolding from this repo's own dogfood folder (confirmed unused dead weight, sat at literal {} its whole life) and logged three explicit product must-not-do decisions: no reopening semantic-retrieval/knowledge-graph (the old V2/V3 items), no moving core .memoryintel/ content to SQLite, and no chasing broad agent-tool adapter coverage (Copilot/Windsurf/Cline/Continue/Aider) before the flagship Claude Code experience is deeper. Also explicitly considered and rejected: shelling out to the user's own graphify CLI as scan's extraction engine - real no-LLM code-graph tool, but would make memoryintel depend on something almost none of its actual users have installed.

What's still genuinely not done: the dashboard has no real file-hierarchy view; research/*/objectives.md scaffolding doesn't flex to project type; pointer-file tools (cursor/agents-md/gemini) show as 'wired' with no 'actually used' signal; a devDependency-only npm audit finding is deferred (dev-only, never ships to consumers); import doesn't yet cover CLAUDE.md/AGENTS.md as a source; scan does no real .gitignore parsing (hardcoded ignore-dir list instead) and has no Go/Rust import-graph support; neither command has a binary-level (spawned-process) test yet, only unit-level. Next candidates being weighed, by priority: a local memoryintel search command (grep-scoped retrieval, no embeddings) as the foundation for later global cross-project search; then a drift/consistency checker cross-referencing memory claims against actual repo state.
