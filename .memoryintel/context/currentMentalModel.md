Memory Intel (npm: `memoryintel`) is a persistent, cross-session project-memory tool for AI coding agents (Claude Code, Cursor, Codex, Gemini CLI). A person sets it up once per project by asking an agent to (\set up persistent memory here\ - the memoryintel skill runs `memoryintel init`); after that, agents load `.memoryintel/` context automatically at session start and update it on their own judgment when something meaningful changes.\n\nThe repo itself was rebuilt from scratch this cycle: a commit had gone out from the user's company network and gotten flagged on the company's side, so the whole GitHub repo was deleted and recreated with fresh git history (single root commit, no trace of the old one), renamed `memory-intel` -> `memoryintel` throughout (plugin id, marketplace id, skill directory, all repo URLs) to match the npm package name, which was already `memoryintel`. The old npm package had also been fully unpublished in the process. Since npm permanently blocks reusing any version number a package name has ever published-then-unpublished, 0.1.0/0.1.1/0.1.2 are all dead forever on this name - republished fresh as `1.0.0` (the user's explicit choice, to mark this as a real clean start rather than leaving a silent 0.1.x gap), now live on the registry with npm Trusted Publishing (OIDC, no token secret) wired to `release-please.yml` for future releases.\n\nThe CLI core (init/import/load/update/status/check-stop/dashboard) is fully built and tested (219 tests passing, all green on the 3-OS CI matrix). Newest command: `memoryintel import` - pulls `memory-bank/` (Cline/Roo/Kilo-Code convention), `ARCHITECTURE.md`, and `README.md`'s lede verbatim into mapped `.memoryintel/` sections, reusing the existing `runUpdate` pipeline wholesale. Deliberately mechanical, not judgment-based: content is tagged as raw/unfiled, left for the agent's next real update to properly re-file. This shipped in response to an explicit, identified gap - the tool worked well for greenfield projects but had nothing for onboarding onto an existing codebase, which is most real projects.\n\nAlso this cycle: deleted the dead `.memoryintel/intelligence/{entities,metadata,relationships}.json` scaffolding from this repo's own dogfood folder (confirmed unused dead weight, sat at literal `{}` its whole life) and reaffirmed, as an explicit product decision, that semantic retrieval / knowledge-graph (the old V2/V3 roadmap items) stay permanently dropped - alongside two other explicit must-not-do calls: never move core `.memoryintel/` content to SQLite (breaks git-diffability/portability for no real performance win at this scale), and don't chase broad agent-tool adapter coverage (Copilot/Windsurf/Cline/Continue/Aider) before the flagship Claude Code experience is deeper.\n\nWhat's still genuinely not done: the dashboard has no real file-hierarchy view; `research/*`/`objectives.md` scaffolding doesn't flex to project type; pointer-file tools (cursor/agents-md/gemini) show as 'wired' with no 'actually used' signal; a devDependency-only npm audit finding is deferred (dev-only, never ships to consumers); `import` doesn't yet cover CLAUDE.md/AGENTS.md as a source, and has no binary-level (spawned-process) test yet, only unit-level. Next candidates being weighed, by priority: a local `memoryintel search` command (grep-scoped retrieval, no embeddings) as the foundation for later global cross-project search; then a drift/consistency checker cross-referencing memory claims against actual repo state.
