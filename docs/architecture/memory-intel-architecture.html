Memory Intel — internals reference

How Memory Intel actually works

A ground-level map of the files, commands, and hooks behind Memory Intel — what runs when, what it touches on disk, and what a person and their agent each experience along the way.

Overview

One command, then nothing to remember

Memory Intel keeps an AI coding agent's understanding of a project alive across sessions — a running "mental model," decisions, architecture notes — without asking anyone to maintain it by hand.

The whole system rests on one deliberate rule: a person runs memoryintel init once, in chat, when they decide a project deserves persistent memory. Everything after that — loading context at the start of a session, deciding whether anything worth remembering happened, writing it down — is the agent's job, triggered automatically, never typed by a person again.

Three pieces make that possible, and each shows up again in every diagram below: the CLI (memoryintel, run via npx, no install required) does all the real file work; the skill (skills/memory-intel/SKILL.md) tells an agent when to reach for the CLI and in what words; the plugin hooks (hooks/hooks.json) fire the CLI automatically at the start and end of every turn, in every project, without ever touching that project's own configuration.

Concepts

Skill, slash command, hook, plugin — which is which

Four different Claude Code mechanisms, easy to blur together because they all live inside the same install. Only one of them is "a thing that decides to run" — the other three are about how and when, not who decides.

MechanismWho triggers itLives inMemory Intel uses it?

Put together: installing the memory-intel plugin is one step that hands Claude Code two things — a skill it can match against a request like "set up persistent memory here," and two hooks that run automatically in every project from then on. There is no slash command anywhere in this design, and no per-project hook setup either.

Why a hook, and not just the skill alone? A skill only runs if the model decides to reach for it — reasonable for a one-time ask like "set up memory," risky for something that must happen at the start of every single session without fail. Loading context and nudging the agent when a diff goes unaccounted for are both promises Memory Intel can't leave to the model's discretion turn after turn, so those two are hooks, not skill judgment calls.
Why a plugin's hooks.json, and not each project's own .claude/settings.json? Both can register the same hooks — the difference is where the config lives and who owns it. Writing into a project's .claude/settings.json means every teammate's checkout needs it written (or committed and hoped to merge cleanly), and it's foreign config a general-purpose tool has no business mutating on a project's behalf. A plugin-level hooks.json registers once, for this machine, and applies to every project automatically — init never touches a project's own settings file at all. This was an explicit design change partway through this project (see docs/superpowers/specs/2026-08-21-plugin-level-hooks-design.md), made for exactly this reason.

And why no slash command? Early on, this project considered one — /memory-intel init, typed by a person. It was dropped in favor of matching plain language instead (following the same pattern graphify uses): a person says "set up persistent memory" in whatever words come naturally, the skill's description matches that intent, and nothing project-specific has to be memorized or typed correctly. The CLI commands underneath (init, load, update, …) still exist — they're just run by the agent via the skill, never typed by a person directly.

Architecture

Where each piece lives, and who it talks to

Three zones: the current project's own .memoryintel/, the machine-wide state under ~/.memoryintel/ shared by every project, and the plugin that wires the two together.

The hooks aren't in this diagram because they aren't a component the CLI talks to — they're a second, independent way the CLI gets invoked. Once the memory-intel plugin is installed, its hooks/hooks.json runs npx -y memoryintel load at the start of every session and npx -y memoryintel check-stop at the end of every turn, in every project, with zero project-level configuration. No project's own .claude/settings.json is ever written.

User & agent journey

From "let's set this up" to background habit

Five phases, in the order a real project moves through them. Left column is what the person experiences; right column is what's actually running underneath.

1 · Discover

Person

Installs the memory-intel skill once — npx skills add <owner>/<repo> --skill memory-intel — and, if they want Claude Code automation, installs the plugin.

System

Nothing project-specific exists yet. The skill and the plugin's hooks/hooks.json are now available to every project on the machine.

2 · Bootstrap

Person

Opens a project, says "set up persistent memory here." Never types a terminal command themselves.

Agent

Skill matches the request, runs npx -y memoryintel init. Reports back in a sentence, not a file listing.

3 · Every session

Person

Opens the project like any other day. Says nothing about memory at all.

Agent

load fires on its own at session start; the agent already has the mental model and active context before the first reply.

4 · While working

Person

Makes real changes — new architecture, a decision, a fix. Keeps working; never asked to log anything.

Agent

Gets nudged once, at most, if it finishes a turn with an unresolved diff. Decides for itself whether the change is worth update — trivial edits are silently skipped.

5 · Later, occasionally

Person

Might open the shared local dashboard to see what the agent currently believes about a project, or say "turn the dashboard off" — a single machine-wide switch, not per-project.

System

The dashboard daemon is lazily started by whichever load/update call notices it isn't running yet — never a separate thing to remember to launch.

Self-compression

Keeping memory cheap to load, without losing why

load() reads its files wholesale into every session. Left unchecked, a project's currentMentalModel.md or technical/architecture.md only ever grows — so the same loop that writes memory needs a safe way to shrink it back down, without quietly discarding something that still mattered.

No new command exists for this. Compaction is drafted as an ordinary update-plan row with one extra field, kind: compress, and applied through the exact same replace path every other update already uses — the only thing that changes is one extra check before the write.

Git is the archive. Nothing compressed away is duplicated into a second file inside .memoryintel/. A cut section is fully recoverable from git history — it just stops being loaded by default. That's also why "cannot determine git status at all" is treated the same as "dirty," not as "safe": an unverifiable file is one where that guarantee can't be confirmed.

The check itself is a signal, not a policy — load() reports status: over and the agent decides, using the same judgment it already applies to whether to update at all, whether this session is a sensible moment to act on it. What actually gets kept or cut is agent judgment, not code, which is where it matters most:

Keep verbatim, never compress away

Architecture decisions and their rationale. Unresolved open questions. Anything a future session would need to avoid repeating a mistake or re-deriving a conclusion already reached.

Safe to compress

Resolved narrative — "tried X, it didn't work, did Y instead" collapses to "Y (not X — see git history for why)." Routine progress entries fully superseded by a later one. Verbose detail a terser statement of the current state already covers.

Rule of thumb, verbatim from instructions.md: if a future session would reasonably ask "why is it built this way?" and the compacted summary can't answer, it compressed too much — keep more.

Complements or contradicts

Does adding Memory Intel fight with what's already there?

Mostly no — the four tools above solve different problems well enough that running Memory Intel alongside most of them is additive, not redundant. One real exception, one direct lineage, one non-issue, one different planet.

vs. claude-mem — complements, with one shared seam

Genuinely different jobs: claude-mem answers "what happened, and when" (a searchable timeline); Memory Intel answers "what's true about this project right now" (a maintained understanding). Different storage, different files, no write conflicts.

The one friction point: both tools register a SessionStart hook that injects context. Running both means two separate context blocks land at the start of every session — not broken, just some avoidable duplication worth being aware of.

vs. Mem0 — complements, different altitude

Mem0's job is cross-application semantic memory — user preferences, facts, anything worth recalling by meaning, across whatever agent framework is calling it. Memory Intel's job is one project's structured understanding. A team could reasonably run both: Mem0 for "the user prefers tabs over spaces," Memory Intel for "here's why the auth service is built this way."

No automatic double-injection risk — Mem0 is invoked explicitly by whatever's calling it, not via a competing session hook.

vs. Cline Memory Bank — direct lineage, pick one

This is the pattern Memory Intel's own PRD was written against, almost file-for-file: projectbrief.md, activeContext.md, progress.md — the same shape, minus every automatic trigger. Running both on one project means two overlapping, competing sets of near-identical files.

If a team is already disciplined about manually saying "update memory bank" every session, Memory Intel is the automated version of the same idea, not an addition to it — a replacement, not a companion.

vs. Zep — different category, comparison doesn't really apply

Zep is built for customer-facing conversational agents — support bots, personal assistants — with a temporal knowledge graph as its core primitive. It has no meaningful overlap with a coding agent's project memory; the two would never compete for the same job, and there's nothing to complement either. Included above only to show the boundary of the category.
